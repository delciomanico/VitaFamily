## 3. Portal da clínica (`ClinicAccount` — D17/D18, ADR-020)

> Espaço de identidade **separado** de `users`/`family_members` (ADR-020): sem FK entre as tabelas
> desta secção e as de `users`/família. Sessões próprias, tokens próprios.

**clinic_accounts**
`clinic_id FK→clinics CASCADE NN` · `email citext NN UNIQUE` · `password_hash text NN` · `role clinic_account_role NN` · `status clinic_account_status NN default 'ACTIVE'` · `created_by_platform_admin FK→users SET NULL` (preenchido só na conta `CLINIC_ADMIN` raiz) · `suspended_at timestamptz`
CHECK `clinic_id` tem de referenciar uma clínica `type='PARTNER'` (garantido no serviço; `clinics.type` não é imutável na BD). UNIQUE parcial `(clinic_id) WHERE role='CLINIC_ADMIN' AND status='ACTIVE'` (uma única conta Admin ativa por clínica, BR-CLN-05). **M14 R (§3f):** `role` ganha `CLINIC_DOCTOR` e a tabela ganha `professional_id`.

**clinic_sessions** — `clinic_account_id FK→clinic_accounts CASCADE NN` · `refresh_token_hash text NN UNIQUE` · `token_chain_id uuid NN` · `user_agent` · `ip inet` · `expires_at NN` · `revoked_at` · `last_used_at NN`
Equivalente a `sessions`, mas para `clinic_accounts`; cadeias de refresh independentes das de `User`.

**clinic_slots** — `clinic_id FK→clinics CASCADE NN` · `kind clinic_slot_kind NN default 'APPOINTMENT'` (D19; migração com default preserva horários existentes) · `specialty text NN` (em `EXAM`: tipo de exame) · `professional_name` · `starts_at timestamptz NN` · `duration_minutes int NN` · `capacity int NN default 1` (vagas, BR-APT-11; migração `0022`, o default preserva horários existentes)
CHECK `duration_minutes` em `(15, 20, 30, 45, 60)` (BR-CLN-04/UC-CLN-04) · CHECK `capacity BETWEEN 1 AND 50` · CHECK `kind = 'EXAM' OR capacity = 1` (consulta sempre 1 vaga). Ocupação **calculada em consulta**, sem coluna derivada: `APPOINTMENT` livre = sem `appointments.slot_id` com `status` em `(REQUESTED, SCHEDULED)` (BR-APT-06); `EXAM` com vaga = `count(examinations WHERE slot_id = slot AND status = 'SCHEDULED') < capacity` (BR-APT-11). **Concorrência:** reservar vaga (criar exame com `slotId`), alterar `capacity` e remover o horário correm numa transação que começa por `SELECT … FROM clinic_slots WHERE id = $1 FOR UPDATE` (bloqueio da linha do horário), depois contam e decidem; cancelar não precisa de bloqueio (só liberta). Detalhe no ADR-023. A compatibilidade `kind` ↔ recurso (consulta só em `APPOINTMENT`, exame só em `EXAM`) é garantida no serviço (não é expressável em CHECK entre tabelas).

### 3a. Catálogo, regras de horário e bloqueios (M14 a1/a2 — ADR-026; migração proposta `0027`)
Todas com `clinic_id FK→clinics CASCADE NN` e `UNIQUE (clinic_id, id)` (alvo das FKs compostas: um profissional/serviço/regra só se liga a horários da **mesma** clínica). Isolamento por `clinic_id` do token (404 sem enumeração). Sem dados Vita nem de saúde.

**clinic_professionals** — `name text NN` (CHECK `char_length BETWEEN 1 AND 120`) · `specialty text` (CHECK `<= 80`) · `active boolean NN default true`. UNIQUE parcial `(clinic_id, lower(name)) WHERE active` (BR-CLN-11).

**clinic_service_types** — `name text NN` (1–120) · `kind clinic_slot_kind NN` (reutiliza o enum; APPOINTMENT = consulta, EXAM = exame; imutável no serviço) · `duration_minutes int NN` (CHECK em `(15, 20, 30, 45, 60)`, o mesmo de `clinic_slots`) · `price_minor bigint` (CHECK `price_minor IS NULL OR price_minor BETWEEN 0 AND 100000000000`; informativo) · `active boolean NN default true`. UNIQUE parcial `(clinic_id, kind, lower(name)) WHERE active`. Moeda: **não há coluna aqui**; vem de `clinics.currency`.

**clinic_schedule_rules** — `professional_id uuid NN` · `service_type_id uuid NN` (FKs compostas `(clinic_id, professional_id) → clinic_professionals(clinic_id, id)` e `(clinic_id, service_type_id) → clinic_service_types(clinic_id, id)`, **`ON DELETE NO ACTION`**: nunca se apagam; a cascata da clínica remove tudo na mesma instrução) · `weekdays smallint[] NN` (CHECK `cardinality(weekdays) BETWEEN 1 AND 7 AND weekdays <@ ARRAY[1,2,3,4,5,6,7]::smallint[]`; unicidade dos elementos validada no serviço) · `start_time time NN` · `end_time time NN` (CHECK `end_time > start_time`) · `valid_from date` · `valid_until date` (CHECK `valid_until IS NULL OR valid_from IS NULL OR valid_until >= valid_from`) · `capacity int NN default 1` (CHECK `BETWEEN 1 AND 50`; `capacity > 1` só com serviço `EXAM` e intervalo ≥ 1 duração: validado no serviço, cross-table) · `active boolean NN default true`.
Sobreposição entre regras ativas do mesmo profissional: validada no serviço sob o bloqueio da linha do profissional (não é expressável em CHECK).

**clinic_time_off** — `professional_id uuid NN` (FK composta como acima, `NO ACTION`) · `starts_at timestamptz NN` · `ends_at timestamptz NN` (CHECK `ends_at > starts_at AND ends_at <= starts_at + interval '366 days'`) · `reason text` (CHECK `<= 200`; nota interna, fora de logs/auditoria) · `created_by_clinic_account_id FK→clinic_accounts SET NULL`.

**clinic_slots (colunas novas, `0027`)** — `professional_id uuid` · `service_type_id uuid` · `schedule_rule_id uuid` (FKs compostas `NO ACTION` para as tabelas acima, com `clinic_id`; nulas nos horários existentes) · `ends_at timestamptz NN` (backfill `starts_at + duration_minutes * interval '1 minute'`; mantida pelo serviço — **não** é coluna gerada porque `timestamptz + interval` não é `IMMUTABLE` e não pode entrar no índice/exclusão).
- CHECK `ends_at = starts_at + duration_minutes * interval '1 minute'` · CHECK `schedule_rule_id IS NULL OR (professional_id IS NOT NULL AND service_type_id IS NOT NULL)`.
- **Exclusão de sobreposição (BR-CLN-13):** `EXCLUDE USING gist (professional_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (professional_id IS NOT NULL)` (intervalo semiaberto por omissão; **requer `CREATE EXTENSION btree_gist`**, extensão *trusted* desde PG 13).
- **Idempotência da geração (BR-CLN-12):** UNIQUE parcial `(schedule_rule_id, starts_at) WHERE schedule_rule_id IS NOT NULL`; a geração usa `INSERT … ON CONFLICT DO NOTHING` e trata a violação da exclusão como `skippedOverlap`.
- **Concorrência:** gerar, criar bloqueio e publicar manualmente com `professionalId` começam por `SELECT … FROM clinic_professionals WHERE id = $1 FOR UPDATE` e só depois bloqueiam horários (`clinic_slots … FOR UPDATE`); reservar (BR-APT-11) continua a bloquear só o horário. Ordem fixa **profissional → horário** (sem deadlocks).

**clinics (coluna nova, `0027`)** — `currency text NN default 'AOA'` (CHECK `currency ~ '^[A-Z]{3}$'`). Só leitura nas fases a1/a2 (exposta em `ClinicServiceType.currency`); a edição fica para a fase (e). O default preserva as clínicas existentes.

**appointments (coluna nova, `0027`)** — `duration_minutes int NN default 30` (CHECK `BETWEEN 5 AND 480`; BR-CLN-16). Backfill: `UPDATE appointments a SET duration_minutes = s.duration_minutes FROM clinic_slots s WHERE a.slot_id = s.id`; as restantes ficam com 30. Interno (não exposto nos contratos da família).

### 3d. Pacientes da clínica, consentimento e visitas (M14 P — ADR-026; migração `0028_clinic_patients.sql`, implementada)
> **Exceção estreita à separação de identidades (ADR-020):** `clinic_patients` e `clinic_visits` **não** têm FK para `users`/família (registo da clínica, sem ids Vita); só `clinic_patient_links`, `clinic_consents`, `clinic_link_codes` (e, desde M14 R, `clinic_receipt_links`, §3f) referenciam `families`/`family_members` (a ligação "vive no servidor", ADR-026). Todas com `clinic_id FK→clinics CASCADE NN`, exceto `clinic_link_codes` (do lado do paciente). Isolamento por `clinic_id` do token (404 sem enumeração). Enums novos (criados na própria migração, sem `ADD VALUE`): `clinic_patient_origin`(MANUAL, VITA) · `clinic_link_via`(EMAIL, CODE) · `clinic_consent_level`(BOOKINGS, HISTORY) · `clinic_visit_status`(SCHEDULED, COMPLETED, CANCELLED).

**clinic_patients** — `name text NN` (CHECK `char_length BETWEEN 1 AND 120`) · `name_norm text NN` (minúsculas sem acentos, mantido pelo serviço; pesquisa) · `phone text` (CHECK `<= 30`) · `phone_digits text` (só dígitos, mantido pelo serviço; pesquisa) · `email text` (CHECK `<= 254`; minúsculas; **só contacto**, nunca cruzado com `users.email`) · `birth_date date` · `notes text` (CHECK `<= 2000`) · `origin clinic_patient_origin NN` · `created_by_clinic_account_id FK→clinic_accounts SET NULL`. `UNIQUE (clinic_id, id)` (alvo de FK compostas). Sem DELETE nesta fase.

**clinic_patient_links** — `clinic_patient_id uuid NN` (FK composta `(clinic_id, clinic_patient_id) → clinic_patients(clinic_id, id)` `CASCADE`) · `family_id FK→families CASCADE NN` · `member_id FK→family_members CASCADE NN` (coerência família↔membro validada no serviço) · `via clinic_link_via NN`. UNIQUE `(clinic_patient_id)` (um membro por paciente) e UNIQUE `(clinic_id, member_id)` (um paciente por membro e clínica). **A única tabela do registo da clínica com ids Vita**; apagar o membro/conta/família apaga a ligação (BR-CLN-24).

**clinic_consents** — `family_id FK→families CASCADE NN` · `member_id FK→family_members CASCADE NN` · `level clinic_consent_level NN` · `history_valid_until timestamptz` · `granted_by_user_id FK→users SET NULL`. UNIQUE `(clinic_id, member_id)`. CHECK `(level = 'HISTORY') = (history_valid_until IS NOT NULL)`. Nível **efetivo** (calculado em consulta, sem job): `HISTORY` se `level='HISTORY' AND history_valid_until > now()`, senão `BOOKINGS`. Revogar = `DELETE` da linha (a história fica na auditoria).

**clinic_link_codes** — `family_id FK→families CASCADE NN` · `member_id FK→family_members CASCADE NN` · `code_hash text NN UNIQUE` (HMAC-SHA256 do código normalizado com `CLINIC_LINK_CODE_SECRET`; nunca o código) · `expires_at timestamptz NN` (criação + 10 min) · `used_at timestamptz` · `created_by_user_id FK→users SET NULL`. Sem `clinic_id` (o código não é de uma clínica). Consumo atómico: `UPDATE … SET used_at = now() WHERE code_hash = $1 AND used_at IS NULL AND expires_at > now() RETURNING …` (1 só vence sob concorrência). Ao gerar um código novo, os ativos do membro ficam com `used_at = now()`.

**clinic_visits** — `clinic_patient_id uuid NN` (FK composta `(clinic_id, clinic_patient_id) → clinic_patients(clinic_id, id)`, `NO ACTION`) · `slot_id FK→clinic_slots(id) SET NULL` (clínica do horário validada no serviço) · `scheduled_at timestamptz NN` · `duration_minutes int NN` (CHECK `BETWEEN 5 AND 480`; copiada do horário, BR-CLN-16) · `status clinic_visit_status NN default 'SCHEDULED'` · `notes text` (≤2000) · `outcome_note text` (≤2000) · `cancel_note text` (≤2000) · `booked_by_clinic_account_id FK→clinic_accounts SET NULL`. UNIQUE parcial `(slot_id) WHERE status = 'SCHEDULED' AND slot_id IS NOT NULL` (uma marcação ativa por horário `APPOINTMENT`); a exclusão cruzada com `appointments` (BR-APT-06) e a sobreposição do paciente/profissional são validadas no serviço **sob o bloqueio do horário** (ordem profissional → horário, §3a). Não referenciada por nenhuma tabela Vita.

### 3e. Confirmação ativa, fluxo do dia e retorno (M14 Q — ADR-026; migração `0029_clinic_day_flow.sql`, implementada)
> Sem tabelas novas: colunas em `appointments` e `clinic_visits` (a confirmação, a chegada e o retorno são atributos da marcação, e apagam-se com ela, D15/BR-CLN-24). Enums novos criados na migração: `appointment_confirmation_status`(PENDING, CONFIRMED, DECLINED) · `confirmation_source`(PATIENT, CLINIC). **`ADD VALUE`** (em transação, PostgreSQL ≥ 12, **sem usar** os valores novos na própria migração): `clinic_visit_status` + `'NO_SHOW'`; `alert_type` + `'APPOINTMENT_CONFIRM_REQUEST'`, `'FOLLOWUP_REMINDER'`. `alert_source` não muda (`APPOINTMENT`).

**appointments (colunas novas, `0029`)** — `confirmation_status appointment_confirmation_status NN default 'PENDING'` · `confirmation_source confirmation_source` · `confirmed_at timestamptz` · `arrived_at timestamptz` · `started_at timestamptz` · `followup_due_on date`.
- CHECK `(confirmation_status = 'CONFIRMED') = (confirmation_source IS NOT NULL AND confirmed_at IS NOT NULL)` · CHECK `confirmation_status <> 'DECLINED' OR status = 'CANCELLED'` (o serviço repõe `PENDING` e anula chegada/início se a consulta é reativada ou muda de `scheduled_at`, BR-CLN-25) · CHECK `started_at IS NULL OR (arrived_at IS NOT NULL AND started_at >= arrived_at)`.
- `followup_due_on`: só tem valor em `COMPLETED` (o serviço limpa-o ao sair de `COMPLETED`, ST4; sem CHECK porque a correção titular `COMPLETED ↔ NO_SHOW` é legítima). `patientNotified` e `waitingMinutes` **não** se guardam (derivados).
- Backfill: `confirmation_status='PENDING'` (default); restantes `NULL`. Consultas antigas já `SCHEDULED` e futuras também recebem o pedido de 48 h se ainda faltar >48 h (o scanner lê o estado atual).

**clinic_visits (colunas novas, `0029`)** — as mesmas seis, com CHECK `confirmation_status <> 'DECLINED'` e `confirmation_source IS NULL OR confirmation_source = 'CLINIC'`. A UNIQUE parcial do horário `WHERE status='SCHEDULED'` mantém-se: `NO_SHOW` liberta a unicidade do índice mas **não** reabre o horário passado (BR-CLN-28; só horários futuros são reservados).

### 3f. Recibos, perfil da clínica e papel Médico (M14 R — ADR-026; migração PROPOSTA `0030_clinic_receipts_profile_roles.sql`)
> Todas as tabelas novas têm `clinic_id FK→clinics CASCADE NN` e isolamento por `clinic_id` do token (404 sem enumeração). **Recibos são registo da clínica** (BR-CLN-24): não têm FK para `appointments`/`examinations`/`clinic_visits` (`booking_id` é um uuid simples, validado no serviço) para sobreviverem ao apagamento Vita; a única ponte para ids Vita é `clinic_receipt_links`. Enums novos (criados na migração): `receipt_booking_kind`(APPOINTMENT, EXAM, VISIT) · `clinic_receipt_status`(ISSUED, VOIDED) · `receipt_payment_method`(CASH, CARD, TRANSFER, INSURANCE). **`ADD VALUE`:** `clinic_account_role` + `'CLINIC_DOCTOR'` (nenhum CHECK/índice da migração usa o literal do valor novo: a CHECK abaixo compara `role::text`; se o runner/PG alvo não o permitir, dividir em `0030_clinic_doctor_role` + `0031_clinic_receipts_profile`).

**clinic_receipt_counters** — `clinic_id FK→clinics CASCADE` **PK** · `last_number int NN default 0` (CHECK `>= 0`). Uma linha por clínica, criada no primeiro recibo (`INSERT … ON CONFLICT (clinic_id) DO UPDATE SET last_number = last_number + 1 RETURNING`, **na transação do recibo**: a linha serializa emissões concorrentes e o número reverte se a transação falha — sem buracos, BR-CLN-32).

**clinic_receipts** — `UNIQUE (clinic_id, id)` · `number int NN` (CHECK `> 0`) · `booking_kind receipt_booking_kind NN` · `booking_id uuid NN` (**sem FK**) · `status clinic_receipt_status NN default 'ISSUED'` · `payment_method receipt_payment_method NN` · `currency char(3) NN` (copiada de `clinics.currency`; CHECK `~ '^[A-Z]{3}$'`) · `total_minor bigint NN` (CHECK `> 0 AND <= 100000000000`) · `patient_name text NN` (retrato; CHECK 1–120) · `note text` (CHECK `<= 200`) · `issuer jsonb NN` (retrato do perfil: `name`, `address?`, `phone?`, `email?`) · `issued_at timestamptz NN default now()` · `issued_by_clinic_account_id FK→clinic_accounts SET NULL` · `voided_at timestamptz` · `void_reason text` (CHECK 3–200) · `voided_by_clinic_account_id FK→clinic_accounts SET NULL`.
- UNIQUE `(clinic_id, number)` (BR-CLN-32) · UNIQUE parcial `(clinic_id, booking_kind, booking_id) WHERE status = 'ISSUED'` (um recibo `ISSUED` por marcação, BR-CLN-31) · CHECK `(status = 'VOIDED') = (voided_at IS NOT NULL AND void_reason IS NOT NULL)`.
- **Imutável** (BR-CLN-33): o serviço só faz `UPDATE` de `status`/`voided_*`; teste de integração obrigatório; sem `DELETE` fora da cascata da clínica.

`policy_id FK→insurance_policies CASCADE NN` · `insurer_id FK→insurer_accounts RESTRICT NN` (= `insurance_policies.insurer_id`, desnormalizado para a FK composta do portal; nunca nulo ao criar o pedido, BR-INS-03) · `amount numeric NN` · `currency char(3) NN` (**sem default**: copiada de `insurer_accounts.currency` na criação, ADR-025/Q1; a migração futura remove o `default 'EUR'` e preserva o valor das linhas existentes) · `encounter_id uuid` (opcional; FK composta `(insurer_id, encounter_id)→insurer_encounters`; atendimento a que o reembolso se refere, BR-SEG-21; `SET NULL`) · `status reimbursement_claim_status NN default 'SUBMITTED'` · `decision_note text` · `decided_by_insurance_account_id FK→insurance_accounts SET NULL` · `decided_at timestamptz` · `submitted_by FK→users SET NULL`

**reimbursement_claim_documents** — associação simples (ADR-021, "sem entidade de anexo nova")
`claim_id FK→reimbursement_claims CASCADE NN` · `document_id FK→documents CASCADE NN`
UNIQUE `(claim_id, document_id)`. É a **única** superfície de documentos que a seguradora vê (BR-INS-04): a aplicação nunca junta `documents` por `member_id` nas rotas `/insurance-portal/*`, só por esta tabela.

**recommendations** (D19, ADR-023; `family_id NN`, `member_id NN`, FK composta CASCADE) — `clinic_id FK→clinics SET NULL` · `clinic_name text NN` · `clinic_account_id FK→clinic_accounts SET NULL` (autor) · `appointment_id FK→appointments CASCADE` · `examination_id FK→examinations CASCADE` · `text text NN`
CHECK `num_nonnulls(appointment_id, examination_id) = 1` · CHECK `char_length(text) BETWEEN 1 AND 2000`. Sem UPDATE/DELETE pela aplicação da clínica (imutável); apaga-se só em cascata.

## 8. Eliminação em cascata (resumo)
`users` → apaga `family_members` com `user_id` (e, por cascata, os seus registos), `sessions`, `auth_tokens`, `alerts`, etc. **Antes** de apagar: o serviço enfileira `file_deletions` para os `storage_key` dos documentos afetados, na mesma transação. `families` → cascata total (inclui `insurance_policies`/`reimbursement_claims`/`reimbursement_claim_documents` do membro, ADR-021). `audit_logs` nunca em cascata. `clinics` → cascata para `clinic_accounts`, `clinic_slots`, `clinic_professionals`, `clinic_service_types`, `clinic_schedule_rules`, `clinic_time_off` (M14: FKs compostas `NO ACTION`, nada apaga profissionais/serviços/regras fora da cascata da clínica; `clinic_accounts` → `SET NULL` em `clinic_time_off.created_by_clinic_account_id`) (ADR-020: independente da cascata de `users`/`families`); `clinic_accounts` → cascata para `clinic_sessions`. Eliminar uma clínica parceira segue BR-CLN-02 (consultas existentes mantêm `clinic_name` em texto; `appointments.clinic_id`/`slot_id` ficam `NULL` por `SET NULL`). `insurer_accounts` → cascata para `insurance_accounts` (ADR-021, mirror de `clinics`→`clinic_accounts`); `insurance_accounts` → cascata para `insurance_sessions`. Como não há "seguradora privada" nem BR-CLN-02 equivalente, não há eliminação de `insurer_accounts` prevista no MVP desta funcionalidade — só suspensão (`status=SUSPENDED`); `reimbursement_claims.insurer_id` é `RESTRICT` por isso.

**M14 P (ADR-026, BR-CLN-24):** `family_members`/`families`/`users` → cascata para `clinic_patient_links`, `clinic_consents` e `clinic_link_codes` (apagar o membro desliga o paciente da clínica); `clinic_patients` e `clinic_visits` **não** são tocadas (registo da clínica, sem ids Vita); `clinics` → cascata para as cinco tabelas de §3d; `clinic_patients` → cascata só para `clinic_patient_links`; `clinic_accounts`/`users` → `SET NULL` nos campos de autoria.

**M14 R (ADR-026, BR-CLN-24/35):** `family_members`/`families`/`users` → cascata para `clinic_receipt_links` (e para `reimbursement_claim_receipts` via o pedido); `clinic_receipts`/`clinic_receipt_lines` **não** são tocados (registo da clínica, retrato sem ids Vita); `clinics` → cascata para `clinic_receipt_counters`, `clinic_receipts`, `clinic_receipt_lines` (e, por elas, `clinic_receipt_links`/`reimbursement_claim_receipts`); `clinic_accounts` → `SET NULL` em `issued_by_clinic_account_id`/`voided_by_clinic_account_id`; remover uma conta Médico não toca em `clinic_professionals`.

**ADR-025:** `insurer_accounts` → `RESTRICT` para todas as tabelas `insurer_*` (sem eliminação de seguradora, só suspensão); `insurer_beneficiaries` → `SET NULL` na ligação ao `family_members` (eliminar o paciente nunca apaga dados da seguradora); `insurer_beneficiary_link_requests` → cascata com `family_members`; `clinics` → `SET NULL` em `insurer_providers.clinic_id`; contas (`clinic_accounts`/`insurance_accounts`) → `SET NULL` nos campos de autoria (rastreabilidade pelo `audit_logs`). A eliminação do `User`/família **não** toca nos dados da seguradora.

**ADR-023:** `recommendations` e `examinations.slot_id`/`recommendations` seguem a origem (cascata); `clinic_accounts` → `SET NULL` em `examinations.issued_by_clinic_account_id`, `recommendations.clinic_account_id`, `documents.uploaded_by_clinic_account_id` (rastreabilidade preservada pelo `audit_logs`); `insurer_accounts` → `SET NULL` em `insurance_policies.insurer_id`.
