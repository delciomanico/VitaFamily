# Vita Family — Migrações (Fase 12)

> **ATUALIZAÇÃO 2026-10-08 (ADR-014/ADR-015, decisão do proprietário):** a implementação é em **Node.js/TypeScript** (Clean Architecture), com Kysely+`pg` e um **runner de migrações próprio** (SQL simples e numerado, tabela de controlo + transação — sem Prisma), pg-boss, **sem Redis**, em **VPS própria** com Caddy, domínio `vitafamily.cassfrei.com`. Onde este documento diz Prisma, `prisma migrate deploy`, Redis, BullMQ ou Jest, ler o equivalente de ADR-014/ADR-015: o runner próprio aplica as migrações SQL antes de arrancar a nova versão.

> Estado: **v0.1**.

## Princípios
1. **Migrações versionadas e imutáveis** depois de aplicadas num ambiente partilhado; correções = nova migração.
2. Geradas pelo Prisma; **constraints avançadas** (índices parciais, FKs compostas, `CHECK`, `NULLS NOT DISTINCT`, tipos `citext`) em migrações SQL manuais, na mesma sequência (ADR-003).
3. Cada migração é pequena e com um único propósito; nomeadas `YYYYMMDDHHmm_descricao`.
4. **Expand → migrate → contract** para alterações com dados: (1) acrescentar nova estrutura compatível, (2) migrar dados, (3) remover a antiga numa migração posterior; nunca remover e acrescentar na mesma release.
5. Migrações **reversíveis em desenvolvimento** (script de *down* guardado junto, NFR-DATA-04); em produção avança-se com correção-para-a-frente e restauro de backup como último recurso.
6. Aplicação em produção: `prisma migrate deploy` como passo **antes** de arrancar a nova versão (ver `deployment.md`).
7. Dados de teste/seed só em desenvolvimento e staging; produção nunca recebe seeds, exceto o **bootstrap** do primeiro Platform Admin (comando CLI explícito, auditado).
8. Antes de uma migração destrutiva em produção: backup verificado + janela comunicada.

## Verificações automáticas em CI
- A BD criada pelas migrações coincide com `schema.prisma` + SQL manual (teste de *drift*).
- Teste de integração valida cada constraint crítica: tutor principal único, isolamento por FK composta, `CHECK` de documentos, `dedupe_key` único.
- Linter de SQL para operações bloqueantes em tabelas grandes (ex.: `CREATE INDEX` sem `CONCURRENTLY` em tabelas de volume).

- **Fase 2 (a fazer nas migrações de M6/M7):** depois de criar `prescriptions` (M6), `ALTER TABLE documents ADD CONSTRAINT documents_prescription_fk FOREIGN KEY (prescription_id) REFERENCES prescriptions (id) ON DELETE CASCADE;`; depois de criar `examinations` (M7), o equivalente para `examination_id` → `examinations`. Ver `apps/api/src/modules/documents/README.md` e o comentário SQL no topo de `0006_documents.sql`.

- **ADR-023 revisto (2026-11-04) — `0022_exam_slot_capacity_and_issuer_checks.sql`** (única migração, transacional; sem `ADD VALUE`; **não edita** `0017`/`0021`, que são imutáveis). Por ordem:
  1. `ALTER TABLE clinic_slots ADD COLUMN capacity int NOT NULL DEFAULT 1` + `CHECK (capacity BETWEEN 1 AND 50)` + `CHECK (kind = 'EXAM' OR capacity = 1)` (expand: horários existentes ficam com 1 vaga).
  2. Migrar dados do fluxo retirado: `UPDATE examinations SET status = 'CANCELLED', response_note = COALESCE(response_note, 'Pedido descontinuado') WHERE status IN ('REQUESTED','REJECTED')`; depois `DROP CONSTRAINT examinations_requested_requires_slot_check` e `ADD CONSTRAINT examinations_no_request_flow_check CHECK (status NOT IN ('REQUESTED','REJECTED'))`. Os valores ficam no enum `exam_status` por compatibilidade (o PostgreSQL não os remove sem recriar o tipo); `alert_type` mantém `EXAM_CONFIRMED`/`EXAM_REJECTED` sem uso. Alertas pendentes dessas origens são apagados: `DELETE FROM alerts WHERE type IN ('EXAM_CONFIRMED','EXAM_REJECTED')`.
  3. `DROP INDEX examinations_slot_active_booking_idx`; `CREATE INDEX examinations_slot_scheduled_idx ON examinations (slot_id) WHERE status = 'SCHEDULED'`; `CREATE UNIQUE INDEX examinations_slot_member_scheduled_uq ON examinations (slot_id, member_id) WHERE status = 'SCHEDULED'` (a contagem de capacidade é feita na aplicação sob `SELECT … FOR UPDATE` do horário, ver `schema.md`).
  4. **Correção da CHECK `issued_by`:** `DROP CONSTRAINT examinations_issued_by_clinic_check` (de `0021`) e `ADD CONSTRAINT examinations_issued_by_clinic_check CHECK (issued_by_clinic_account_id IS NULL OR issued_by = 'CLINIC')`; idem `prescriptions_issued_by_clinic_check` (de `0017`) → `CHECK (issued_by_clinic_account_id IS NULL OR issued_by = 'CLINIC')`. Resultado: `ON DELETE SET NULL` da conta da clínica já não viola a CHECK.
  6. **Correção da CHECK do resultado da consulta:** backfill `outcome_recorded_at = COALESCE(outcome_recorded_at, now())` onde `clinic_outcome_note IS NOT NULL`; `DROP CONSTRAINT appointments_outcome_requires_clinic_account_check` (de `0017`) e `ADD CONSTRAINT appointments_outcome_requires_recorded_at_check CHECK (clinic_outcome_note IS NULL OR outcome_recorded_at IS NOT NULL)`. Mesmo defeito que o ponto 4: `ON DELETE SET NULL` da conta já não viola a CHECK. (Ordem de aplicação: este ponto vem depois do 5.)
  5. **Marca permanente do PDF:** `ALTER TABLE documents ADD COLUMN uploaded_by_clinic boolean NOT NULL DEFAULT false`; backfill `true` onde `uploaded_by_clinic_account_id IS NOT NULL` ou (`uploaded_by IS NULL` e o exame tem `scheduled_at IS NOT NULL` ou `issued_by = 'CLINIC'`); `DROP CONSTRAINT documents_clinic_upload_examination_only_check`; `ADD CONSTRAINT` `uploaded_by_clinic_account_id IS NULL OR uploaded_by_clinic` e `NOT uploaded_by_clinic OR (examination_id IS NOT NULL AND uploaded_by IS NULL)`.
